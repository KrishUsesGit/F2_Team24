HOP 01

Executive Summary

HOPTRACE's core instinct — correlate an application symptom with per-hop network telemetry, and say where degradation begins rather than what caused it — is sound and academically defensible. Nothing about it needs to be abandoned. But as scoped, it borrows the shape of a monitoring dashboard (ThousandEyes, PingPlotter) when its actual contribution should be a correlation algorithm with a rigorous, evaluated confidence model, tested against known ground truth. The dashboard is a delivery mechanism for that algorithm, not the project.

Three changes turn this from "a nicer traceroute UI" into a real systems contribution:

  1. Make the controlled testbed the primary evaluation vehicle, not a demo prop — the live internet has no ground truth, so claims about accuracy can only be made inside the testbed.
  2. Replace ad-hoc thresholding ("hop > 80ms = bad") with a changepoint-detection-based correlation engine borrowed from the network-tomography and time-series literature, because that's what makes the confidence numbers meaningful instead of decorative.
  3. Co-locate the application client and the path prober on the same host. This single design choice removes the hardest infrastructure problem in the whole project — cross-host clock synchronization — for free.

With those changes, this is a strong, demonstrable, viva-defensible Computer Networks project. Without them, it's a well-built dashboard that happens to display two charts next to each other and asks the viewer to eyeball the correlation — which is exactly what MTR + ThousandEyes already let you do manually.

HOP 02

Problem Validation

Is the problem well-defined? Partially, and the imprecision matters. "Where does degradation begin" is answerable only if you first fix what you're measuring degradation of. There are two different questions hiding in the one sentence:

  • Path-probe framing: where does a synthetic probe (ICMP/UDP/TCP with incrementing TTL) start showing elevated RTT? This is well-defined and directly measurable.
  • Application-forwarding framing: where does the actual application traffic start being delayed? This is not directly measurable — you cannot get a router to timestamp your WebSocket packets as they pass through. You can only infer it from the probe framing and hope the two are close enough.

HOPTRACE has to be explicit, everywhere in its output, that it answers the first question and treats the second as an inference resting on an assumption: that synthetic probes and application packets experience comparable per-hop treatment. That assumption is reasonable but not guaranteed — see below and Failure Cases.

Is application-to-hop correlation actually feasible?

At the level the brief wants — temporal correlation between an app-level onset and a path-level onset, localized to a hop range with a stated confidence — yes, feasible, and this is essentially what production systems like Microsoft's Pingmesh and Meta's NetNORAD do at data-center scale for their own operators. At the level of definitively attributing causation to a specific router — no, and no existing tool claims to do that either, for reasons rooted in traceroute's own physics (rate-limited ICMP generation, path asymmetry, and hops that deprioritize diagnostic traffic relative to forwarded traffic all mean a slow hop reply is not proof of a slow forwarding path). This is precisely the distinction the brief itself insists on (OBSERVED FACT vs. INFERENCE vs. CORRELATION), so the project is validating its own founding constraint correctly — the risk is only in the implementation drifting away from it under demo pressure.

Grounding claim

The academic literature that treats this rigorously is network tomography — specifically Boolean network tomography, which formalizes exactly this problem (inferring internal link/node failures from end-to-end path measurements) and proves hard identifiability limits: some sets of failure locations are mathematically indistinguishable given the available vantage points and paths. A single client tracing a single path toward a single server — which is what HOPTRACE's live demo does — is close to the weakest possible vantage-point configuration in this literature. That's not a flaw to hide; it's the reason the system must report ranges and confidence instead of single points, and it gives the project a real citation trail instead of reinventing the idea from scratch.

HOP 03

Existing Solutions / Competitive Landscape

None of the following tools do what HOPTRACE proposes to do — but each does a piece of it better than a first pass at HOPTRACE would, and the review has to be honest about that before claiming novelty.

ToolWhat it does wellWhat it does not do
traceroute Baseline hop discovery via TTL expiry; universally available. Single-shot, no persistence, no app correlation, no statistics.
MTR / WinMTR Continuous per-hop RTT + loss sampling in real time; the standard "is it my ISP" tool. Pure network layer. No application signal, no ground truth, no confidence — the human reads the table and decides.
PingPlotter Time-series graphing of per-hop latency/loss, alerting, historical replay. Same gap as MTR: no application-layer integration, no automated localization.
ThousandEyes The closest existing analog. Runs genuine Path Visualization (multi-round traceroute-style probing, ECMP fan-out shown as branching paths) alongside separate application/HTTP-layer tests, from many vantage points, with 16+ metadata categories per hop. The correlation between the app-layer chart and the path chart is left to the human analyst reading two dashboards side by side. Public documentation shows no automated "app onset ≈ hop N onset, confidence X" output — that step is exactly the gap HOPTRACE can fill, if it fills it rigorously rather than cosmetically.
Pingmesh (Microsoft) / NetNORAD (Meta) Continuous all-pairs active probing at data-center scale with statistical baselining, detecting silent packet drops and faults in production fabrics within seconds. Operate where the operator owns both endpoints and every hop in between — a fundamentally easier inference problem than an uncontrolled Internet path. Good precedent for the probing pattern, not a substitute for the localization problem HOPTRACE targets.
Network tomography (academic) Rigorous math for inferring internal link/node state from end-to-end measurements, with formal identifiability bounds. Largely theoretical / simulation-evaluated; rarely paired with a real application-layer symptom or a reproducible physical testbed with injected ground truth.

The honest summary: MTR gives you the per-hop data, ThousandEyes gives you the per-hop data and the app data side by side, and academic tomography gives you the statistical rigor for turning ambiguous end-to-end measurements into localization claims with stated confidence. No one publicly documented system combines all three with a ground-truth-evaluated algorithm. That combination is where HOPTRACE should live.

HOP 04

What Is Actually Novel About HOPTRACE

Reframed honestly, the contribution is not a new measurement technique (traceroute is 35+ years old) and not a new statistical technique (changepoint detection and Boolean tomography both predate this project by decades). The legitimate, defensible contribution for a strong undergraduate/graduate Computer Networks project is:

  1. A system that synchronizes application-level and path-level probing on a single clock and treats their temporal alignment as the primary signal, rather than treating each stream as an independently-read chart.
  2. An algorithm that turns that alignment into a hop-range estimate using changepoint detection and downstream-persistence logic (see §11), instead of a fixed latency threshold.
  3. An explicit, enforced evidence taxonomy (fact / inference / correlation / confidence / unknown) that governs every output string the system produces — turning "technical honesty" from a writing-style rule into a structural constraint on the software.
  4. A ground-truth evaluation: dozens of controlled trials with a known fault location, type, and magnitude, scoring the algorithm's localization accuracy, false-attribution rate, and confidence calibration — the part no consumer tool publishes, because they don't need to; a course project does.

That's a legitimate, citable, demonstrable contribution. It is a contribution about evaluated correlation under uncertainty, not about network measurement itself — which is exactly the framing that survives a skeptical viva panel asking "isn't this just MTR with extra steps?"

HOP 05

Refined Problem Statement

Working statement

Given synchronized time series of (a) application-level performance events from a controlled real-time client/server application, and (b) repeated per-hop path measurements (RTT, loss) collected along the same route from the same vantage point, design and evaluate an algorithm that estimates the network segment at which performance degradation first becomes observable in the measured data — together with a calibrated confidence label — and validate that estimate against known fault locations injected in a controlled, multi-hop Linux testbed.

Compared to the original framing ("where along the path does degradation begin"), this version fixes three ambiguities: it names the two data sources explicitly, it commits to "observable in the measured data" rather than "in reality" (the honesty distinction from §2), and it makes the ground-truth testbed part of the problem statement itself rather than an optional add-on — because without it, "estimate" has no way to be shown correct or wrong.

HOP 06

Refined Project Objectives

  • O1 — Instrumented testbed. Build a reproducible multi-hop Linux path (namespaces + veth + tc/netem) with a fault-injection controller that logs ground truth independently of anything HOPTRACE measures.
  • O2 — Synthetic application with real symptoms. Build a small WebSocket client/server that produces a genuine, measurable, timestamped performance signal under load — not a proxy for "fun," a proxy for "latency-sensitive interaction."
  • O3 — Path measurement engine. Continuous, flow-consistent, multi-probe-per-hop measurement that survives ECMP and rate-limited ICMP well enough to be usable, and says "unknown" when it can't.
  • O4 — Correlation / localization engine. Changepoint-based onset detection on every series, downstream-persistence scoring, and a hop-range output with confidence — this is the thesis of the project.
  • O5 — Evidence-constrained reporting. Every user-facing statement is generated from the fact/inference/correlation/confidence/unknown taxonomy; no string in the UI is allowed to assert unmeasured causation.
  • O6 — Ground-truth evaluation. A repeatable experiment harness producing accuracy, precision/recall, false-attribution rate, detection latency, and confidence-calibration numbers across a fault-injection matrix.
  • O7 — Demonstration. A 5–10 minute live run showing detection, localization, and recovery against a fault the audience can see being injected in real time.

Objectives are ordered by dependency, not by drama — O4 is the intellectual center of the project, but O1–O3 have to exist first because O4 has nothing to run on otherwise, and O6 is what separates this from a demo.

HOP 07

Proposed System Architecture — Critique of the Original

The original diagram (UI → Analysis API → {Path Measurement Engine, Application Telemetry} → Fault Localization Engine → Evidence) is the right shape at a coarse level, but it's missing two components that the rest of this review depends on, and it under-specifies the one component that matters most:

  • Missing: a Ground-Truth / Fault-Injection Controller. Without it as a first-class component, "evaluation" has nothing to compare against — it can't be bolted on later, because ground-truth logging has to be independent of (and never visible to) the localization engine, or the evaluation is circular.
  • Missing: an explicit Time-Sync boundary. The diagram implicitly assumes application timestamps and hop timestamps land on a shared timeline. They don't, unless the architecture forces it — see §9 for the fix (co-location, not NTP).
  • Under-specified: the Fault Localization Engine is drawn as one box. It is actually at least three distinct stages — per-series changepoint detection, cross-series alignment, and evidence classification — and treating it as one undifferentiated box is exactly how a project ends up with an "if latency > threshold" one-liner standing in for the actual contribution.

The refined, final version of this diagram is in §21; §8–§12 justify each piece of it individually.

HOP 08

Component-by-Component Design

Application Client + Path Prober (co-located)

Runs on the vantage-point host. Owns one wall clock. Emits two synchronized time series against that single clock: application RTT events and per-hop probe RTT/loss events. See §9 and §10.

Fault Injection / Ground-Truth Controller

Runs against the testbed only (never against the live-internet demo path, where ground truth is unknowable). Applies and removes tc netem impairments on a named interface at a scheduled time, and writes an immutable ground-truth log: {hop, impairment_type, magnitude, t_start, t_end}. This log is consumed only by the evaluation harness (§15), never by the localization engine — the engine must not see the answer key.

Correlation / Localization Engine

Three internal stages, each independently testable: (1) per-series onset detection, (2) cross-series alignment and downstream-persistence scoring, (3) evidence classification into the fact/inference/correlation/confidence/unknown taxonomy. Detailed in §11–§12.

Analysis API + Store

A thin API over a time-series buffer (in-memory ring buffer is sufficient for a course project — no need for a real TSDB). Serves the UI and the evaluation harness identically, so the demo and the experiments are provably running the same code path.

UI

Path visualization, application-lag chart, and an "evidence panel" that renders using the tag taxonomy from §12 — not free-text sentences generated ad hoc, but strings assembled from typed evidence objects, so the UI is structurally incapable of asserting something the engine didn't classify as fact.

HOP 09

Application Telemetry Design

The brief's WebSocket instinct is right; two refinements make it load-bearing rather than decorative.

What it should contain

  • Fixed-cadence timestamped ping/ack messages (10–20 Hz) carrying a monotonic sequence number and client send-time.
  • Server echoes the sequence number and its own receive time immediately — the metric that matters is client-measured round-trip time, computed entirely from the client's own clock.
  • A simple simulated interaction layer on top (e.g. a client-driven "input" event the server must acknowledge within a target budget) gives a second, more app-shaped signal beyond raw RTT, without depending on any proprietary game.
Key design decision

Measure RTT, not one-way delay, and compute it on a single clock. One-way application latency requires the client and server clocks to be synchronized to within a few milliseconds — NTP alone often isn't good enough over consumer links, and getting this wrong silently corrupts every downstream correlation. RTT sidesteps the problem entirely: it's t_receive − t_send, both timestamps taken by the same clock. This is exactly why traceroute and ping use RTT too — it's not a simplification, it's the standard way to avoid needing synchronized clocks across hosts.

Where it runs, and why that decision matters more than the protocol

Run the WebSocket client and the path prober (§10) as two processes on the same physical host, sharing one clock. This means the "temporal correlation" step in §11 never has to reconcile two different machines' notions of time — the hardest, most failure-prone piece of a naive design (cross-host NTP/PTP sync) is eliminated by an architecture choice rather than solved by more code. This is the single highest-leverage change from the original brief.

HOP 10

Network Path Measurement Design

  • Probe protocol: UDP or TCP SYN probes with incrementing TTL, not plain ICMP echo. Routers frequently rate-limit and deprioritize ICMP relative to forwarded traffic; a UDP/TCP probe sharing the application's transport family is a closer (still imperfect) proxy for how the application's own packets are treated.
  • Flow consistency (paris-traceroute style): keep the 5-tuple used for hashing constant across an entire probing round. Without this, per-flow ECMP load balancing makes "hop 3" mean a different physical router on every probe, silently corrupting hop identity.
  • Repeated probing per hop, not single-shot: each hop needs multiple samples per round to distinguish a transient spike from a persistent shift — this is what feeds the changepoint detector in §11 instead of a single noisy point.
  • Hop persistence tracking: record whether the responding IP at a given TTL is stable across rounds; flag instability rather than silently trusting whichever address answered most recently.
  • Non-responding hops: tag as UNKNOWN, not interpolated or skipped. A silent hop is a real, common outcome (ICMP rate-limiting, firewalled routers) and the localization engine must treat it as missing data, not as "zero latency."
HOP 11

Fault Localization / Correlation Approach

This is the actual thesis of the project. The algorithm has three stages:

  1. Per-series onset detection. Run a changepoint detector (a simple CUSUM or a Bayesian online changepoint model — either is a defensible, well-cited choice) independently on the application RTT series and on each hop's RTT/loss series, producing an onset time (or "no changepoint found") per series.
  2. Downstream-persistence alignment. Find the shallowest hop i whose onset time falls within a small window of the application's onset time and where every hop from i through the server also shows a concurrent onset, while hops upstream of i do not. This persistence pattern is what separates "the degradation starts here and continues" from "hop 3 just had a noisy blip" — a single hop spiking in isolation, with no downstream continuation, is explicitly evidence against localizing there.
  3. Evidence classification. The output of stage 2 is passed through the taxonomy in §12 before it ever reaches a UI string.
Fig. 1 — Onset alignment: hop 2 shows no changepoint; hops 3 and 4 shift concurrently with the application series. The algorithm reports "degradation first appears at hop 3, persists downstream" — not "hop 3 caused it."
HOP 12

Evidence + Confidence Model

This is the mechanism that enforces the brief's "technical honesty" requirement as software behavior, not prose style. Every claim the system emits carries one of five tags:

Fact directly measured — a raw RTT/loss sample.
Inference derived via a stated model — e.g. a changepoint location.
Correlation temporal association only — no causal claim.
Confidence a calibrated score attached to an inference.
Unknown insufficient evidence — reported explicitly, not guessed.

Confidence is computed from named, inspectable factors — not a black-box score:

  • statistical strength of the changepoint (effect size relative to baseline noise);
  • number of downstream hops corroborating the onset;
  • hop-identity stability across the trial (a flapping ECMP path lowers confidence);
  • completeness of response data (more UNKNOWN hops lowers confidence);
  • consistency across repeated trials, where repetition is available.
Acceptable output

Correlation Application degradation is temporally correlated with a path-level change. Inference Evidence is consistent with degradation first appearing at or after Hop 3. Confidence: high (4/4 downstream hops corroborate, stable hop identity, 0 unknown hops).

Never acceptable

"Hop 3 is causing the lag." "Your ISP router is broken." Any string that omits the tag it belongs to, or that a UI component can render without one.

HOP 13

Controlled Testbed Design

Linear topology, 4–5 hops, built from Linux network namespaces and veth pairs, each "router" namespace doing real IP forwarding with static routes — not Docker's own bridge networking, which fights a custom topology instead of exposing one (see §19).

NodeRoleNotes
ns-clientApp client + path proberSingle clock owner (§9)
ns-r1 … ns-r3Forwarding routersip_forward=1, static routes, tc netem attachment point per hop
ns-serverApp server + probe responderGround truth never visible here either
fault-controllerInjects/removes netem qdiscs on scheduleWrites ground-truth log; not readable by the engine

Impairment types to support: added latency, jitter (normal-distribution delay variance), packet loss (including Gilbert-Elliott bursty loss, more realistic than uniform loss), and bandwidth capping — all via tc qdisc … netem on the specific veth interface representing the target hop. A stretch (not core-scope) extension is a small ECMP mesh to test hop-identity stability under load balancing; keep it out of the primary evaluation topology (§24).

HOP 14

Ground-Truth Experiments

A factorial trial matrix, each cell run multiple times for statistical power:

FactorLevels
Fault locationhop 1, 2, 3, (server-adjacent)
Fault typelatency, jitter, loss, bandwidth cap
Magnitudemild / moderate / severe, relative to baseline noise floor
Durationtransient (few seconds) vs. sustained
Probe conditionsnormal, one non-responding hop, simulated ICMP rate-limit

Each trial logs: ground-truth hop/type/magnitude/window (from the controller, §8), HOPTRACE's reported hop range and confidence, and detection latency (elapsed time from actual injection to reported detection). Multi-fault trials are a reasonable stretch goal once the single-fault matrix is solid — not before.

HOP 15

Evaluation Metrics

  • Localization accuracy: exact-hop match rate, and within-±1-hop match rate (the tomography identifiability limits in §2 predict exact-hop accuracy will be lower than within-1-hop — report both, and explain the gap rather than hide it).
  • Precision / recall on the binary "degradation detected at all" classification per trial.
  • False attribution rate: trials where the system reports high confidence at the wrong hop — this is the single most important number for the honesty claim, and it should be reported even if it's not flattering.
  • Detection latency: time from injection to report.
  • Confidence calibration: a reliability diagram — do "high confidence" trials actually land correct more often than "low confidence" ones? A system whose confidence score doesn't correlate with correctness is worse than useless, because it's actively misleading.
  • Robustness sweeps: accuracy as a function of injected probe loss, jitter, and fraction of non-responding hops.
HOP 16

Failure Cases and Limitations

  • ECMP hash flapping mid-trial changes which physical router answers at a given TTL, corrupting hop-identity continuity. Mitigation: hop-persistence tracking (§10) plus confidence penalty; cannot be fully solved on a real multipath internet path.
  • Reverse-path-only impairment. ICMP TTL-exceeded replies travel back over whatever the return path is, which may differ from the forward path. An impairment only on the return leg can make degradation look like it starts near the client, not near the true forward-path hop — a fundamental traceroute limitation, not a bug in this project. Worth demonstrating deliberately as a known limitation rather than discovering it live.
  • Probe deprioritization without application impact. A router that rate-limits diagnostic traffic under load can produce a "slow hop" that forwarded application packets never actually experience — the false-positive case the brief explicitly warns about. TCP/UDP probes (§10) and downstream-persistence scoring (§11) reduce but do not eliminate this; it must remain a stated limitation, not a solved problem.
  • Non-responding hop directly at the fault. If the impaired router itself drops or rate-limits probes, its own data point may be UNKNOWN exactly where the answer is needed most — the algorithm should localize to the surrounding known hops with reduced confidence rather than guess.
  • Overfitting to the clean testbed. A namespace/veth topology has none of the real internet's queueing diversity, hidden middleboxes, or genuine ECMP entropy. Report testbed accuracy as testbed accuracy — never claim it generalizes to arbitrary internet paths without separately qualified evidence.
HOP 17

Live Demonstration Plan

0–1 min

Healthy baseline

Show the path visualization (4 hops, all green) and the application lag chart flat and low. State what "normal" looks like numerically.

1–2 min

Inject a known fault

From the fault-injection controller, add +100 ms latency at hop 3, visible to the audience as a terminal command with a timestamp — this is the ground truth, shown openly, not hidden.

2–4 min

Observe both signals move

Application lag chart shows the onset; per-hop chart shows hops 3–4 shifting while hops 1–2 stay flat. Narrate what's observed before the system says anything.

4–5 min

HOPTRACE reports

The evidence panel renders: correlation detected, inference "at or after hop 3", confidence and the factors behind it — using the exact tag vocabulary from §12.

5–7 min

A harder case

Inject a milder, jitter-only fault, or one on a non-responding hop, and show the confidence score drop and an honest "insufficient evidence" output — this is more convincing than another clean success, because it shows the confidence model is real.

7–9 min

Remove the fault, show recovery

Both series return to baseline; the evidence panel updates to reflect recovery.

9–10 min

One evaluation slide

Localization accuracy, false-attribution rate, and the calibration diagram from the full trial matrix — the demo shows one trial live, this slide proves the algorithm was tested on dozens.

HOP 18

Security / Ethics

  • Scope of probing: active probing (traceroute-style TTL probes, repeated at a controlled cadence) must be restricted to the testbed and, for the live-internet demo mode, to destinations the operator is authorized to probe against — the user's own infrastructure, or well-known public measurement targets that explicitly permit it. Never probe arbitrary third-party hosts at the cadence this system uses; that reads as reconnaissance or a low-grade denial-of-service pattern even when unintentional.
  • Permissions required: raw-socket / traceroute-style probing typically needs elevated privileges (CAP_NET_RAW or root) on Linux — document this requirement plainly and run with the minimum privilege that works, not as root by default.
  • Privacy: resolved hop IPs can reveal ISP infrastructure and rough geolocation; don't persist or publish raw path data beyond what's needed for the evaluation write-up, and avoid logging the identities of any real third-party networks touched during a live-internet demo.
  • Safe testing boundary: the fault-injection controller must only ever be capable of touching interfaces inside the testbed's own namespaces — it should be architecturally incapable of reaching a real production interface, not merely instructed not to.
  • Responsible framing: the evidence taxonomy in §12 is also an ethics control — a tool that could plausibly be read as accusing a specific ISP or router of a fault carries real reputational stakes if it's wrong, which is one more reason the fact/inference/correlation split isn't optional polish.

HOP 20

What I Would Change From the Original Idea

  1. Co-locate the application client and path prober on one host to make temporal correlation a single-clock problem, not a cross-host sync problem.
  2. Make the controlled testbed the primary evaluation vehicle and demote the live-internet path to a qualitative, heavily-caveated demo mode — accuracy claims can only be made where ground truth exists.
  3. Replace threshold-based fault detection with changepoint detection + downstream-persistence scoring, grounded in the time-series and Boolean-tomography literature, so confidence numbers mean something.
  4. Elevate the fault-injection/ground-truth controller to a first-class architecture component from day one, not something added before the evaluation chapter is due.
  5. Use UDP/TCP probes instead of plain ICMP to reduce (not eliminate) the probe-deprioritization false-positive risk.
  6. Structurally enforce the evidence taxonomy — typed evidence objects the UI renders from, not free-text templates a developer might loosen under demo pressure.
  7. Explicitly scope out multi-fault and ECMP-mesh scenarios for v1 — they're real and interesting but would dilute a single-semester project's ability to finish the ground-truth evaluation properly.
  8. Plan the Linux environment (WSL2/VM) up front, since the working environment here is Windows and the testbed's core tools (network namespaces, tc) require a real Linux kernel.

Phase-by-Phase Implementation Roadmap

Environment + testbed skeleton

WSL2/VM set up; namespaces, veth chain, and static routing for a 4–5 hop linear path; verify end-to-end connectivity and a manual tc netem impairment before writing any measurement code.

Phase 1

Path measurement engine

Flow-consistent TTL probing, per-hop repeated sampling, hop-persistence tracking, UNKNOWN handling. Validate against the testbed's known topology.

Phase 2

Application telemetry

WebSocket client/server, RTT ping/ack at fixed cadence, co-located with the prober on one clock.

Phase 3

Fault-injection controller

Scriptable, timestamped impairment injection with an independent ground-truth log.

Phase 4

Correlation engine v1

Changepoint detection + downstream-persistence logic; validate manually against a handful of known trials before automating evaluation.

Phase 5

Evaluation harness

Run the full fault matrix (§14), compute the metrics (§15). This phase is what makes the project defensible — do not compress it to make room for UI polish.

Phase 6

UI + demo polish

Evidence-panel rendering from typed objects, path visualization, rehearsed demo script (§17).

Phase 7 (stretch)

Robustness extensions

ECMP mesh, asymmetric-path handling, multi-fault trials — only after Phase 5's numbers exist.

HOP 23

Biggest Technical Risks

  • Building the testbed on Windows without planning for it. Namespaces and tc need a real Linux kernel; discover this in Phase 0, not Phase 4.
  • Clock-sync mistakes if the co-location decision (§9) is skipped or half-implemented — this single issue can quietly invalidate every correlation result without triggering an obvious error.
  • ICMP/probe deprioritization producing a confident false attribution that no amount of engineering fully removes — the mitigation is the confidence model and honest reporting, not a claim of having solved it.
  • Scope creep toward "a ThousandEyes clone" — more dashboard features instead of a better-evaluated algorithm is the most likely way this project drifts off its own thesis.
  • Overfitting the algorithm to the clean testbed and presenting testbed numbers as if they generalized to arbitrary internet paths.
  • Compressing Phase 5 (evaluation) under deadline pressure — this is the phase most likely to be cut, and it's the one the whole review argues is the actual contribution.
HOP 24

What Must Not Be Built / Out of Scope

  • A general-purpose network monitoring dashboard (a Grafana/PingPlotter clone) — the UI exists to present the correlation result, not to compete on charting features.
  • Integration with proprietary game telemetry (Valorant, Fortnite, etc.) — already correctly excluded in the brief; keep it excluded.
  • Multi-tenant / SaaS infrastructure, accounts, or a production deployment.
  • BGP-level route analysis or AS-path attribution — a different, much larger problem than hop-level temporal correlation.
  • Active probing of arbitrary third-party internet hosts at monitoring cadence — an authorization and ethics problem (§18), not just a scope one.
  • "AI root-cause" framing or any ML black box whose output isn't traceable back to the fact/inference/correlation/confidence taxonomy.
  • Multi-fault simultaneous localization and full ECMP-mesh robustness — real and interesting, correctly deferred to Phase 7 stretch goals, not core deliverables.
  • Mobile clients or non-web UI surfaces.
Final Decision

YELLOW — strong concept, specific changes required before implementation

The core idea — temporally correlating an application symptom with per-hop path telemetry to localize (not attribute) where degradation begins, under an explicit evidence/confidence taxonomy, evaluated against known ground truth — is technically sound, has real academic grounding (Boolean network tomography, changepoint detection literature), and fills a genuine gap left open by MTR, PingPlotter, and even ThousandEyes, all of which stop short of an automated, evaluated correlation step. It is not novel as a measurement technique; it is potentially novel as an evaluated system.

Before writing implementation code, make these changes explicit and locked in:

  1. Co-locate the application client and path prober on one host, on one clock (§9, §20.1).
  2. Commit to the controlled testbed as the primary evaluation vehicle; treat the live-internet path as a qualitative demo only (§20.2).
  3. Replace any threshold-based detection with changepoint detection + downstream-persistence scoring (§11, §20.3).
  4. Build the fault-injection/ground-truth controller as a first-class component from the start, structurally isolated from the localization engine (§8, §21).
  5. Enforce the fact/inference/correlation/confidence/unknown taxonomy as typed data the UI renders from — not a style guideline for prose (§12, §20.6).
  6. Plan the Linux testbed environment (WSL2 or a VM) before Phase 1, given the current working environment is Windows (§19, §23).
  7. Explicitly cut multi-fault and ECMP-mesh scenarios from v1 scope (§20.7, §24).

With those seven changes in place, this is a technically deep, experimentally defensible, viva-ready Computer Networks project — and one whose central claim can actually be measured, not just demonstrated.
