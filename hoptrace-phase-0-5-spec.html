§01

Reading This Spec

Every design decision below is tagged Locked or Open. Locked means: implement it exactly as written, do not re-derive it during coding. Open means: a specific, named decision is still outstanding, and §11 collects every one of them in one place with what's needed to close it. Nothing in Phase 0–3 has an open dependency that blocks starting; Phase 4's algorithm choice is deliberately left open because it is itself the output of an experiment specified in §08, not a decision made in this document.

Schemas are given as JSON Schema-style field lists, not full validators. Interfaces are given as typed signatures, not implementations — this document specifies contracts between components, it does not write the components.

§02

Global Constraints

Binding across every phase — restated from the approved review as hard constraints, not preferences:

Locked

C1 — Single clock. The application client and the path prober run as two processes/threads on the same host, reading the same monotonic clock (CLOCK_MONOTONIC). No component may compute a duration from two timestamps taken on different hosts.

Locked

C2 — Testbed is the evaluation vehicle. All accuracy, precision/recall, false-attribution, and calibration numbers in the final report are computed exclusively from testbed trials with logged ground truth. Any live-internet run is labeled "qualitative demonstration — no ground truth" in every artifact that shows it.

Locked

C3 — No thresholds without a changepoint model behind them. The localization engine's onset detection stage must be one of the candidates in §08, selected by the experiment in §08, not a hand-picked constant.

Locked

C4 — Ground truth is structurally unreadable by the engine. Enforced at the OS/process level per §04, not by convention.

Locked

C5 — Every engine output is a typed evidence object. No component downstream of the correlation engine may construct a user-facing string that asserts causation; only the evidence-object renderer (§06, EvidenceRecord) may produce report text, and only from the five permitted tags (fact / inference / correlation / confidence / unknown).

Locked

C6 — Testbed runs on a real Linux kernel. WSL2 or a Linux VM/cloud instance; network namespaces and tc are not available on native Windows.

Locked

C7 — v1 scope excludes multi-fault trials and ECMP-mesh topologies. The topology in §03 is strictly linear; multiple simultaneous faults are not part of the Phase 0–5 evaluation matrix.

Locked

C8 — Fault terminology. tc netem impairs a router's egress interface / link segment. It does not prove the router itself is faulty. Every log line, code comment, evidence string, and UI label uses "degradation first appears at/after Hop N" or "Hop N onward" — never "Hop N caused the lag" or "Router N is faulty." This applies to internal engineering artifacts (commit messages, code comments) as well as user-facing output — the discipline degrades if it's only enforced at the UI layer.

Locked

C9 — Confidence-model data separation. Phase 4a produces tuning/training data only. Phase 4 selects and freezes the changepoint algorithm, its hyperparameters, the δ_align tolerance, and the confidence-score weights — all four, together, as one frozen artifact. Phase 5 uses a completely held-out test set for final evaluation only. No weight, hyperparameter, or tolerance may be fitted, adjusted, or re-derived using Phase 5 results, under any circumstance, including a disappointing Phase 5 result — a disappointing result is reported, not used to retroactively retune Phase 4.

§03

Testbed Topology

Locked Six network namespaces on one Linux host, connected linearly by point-to-point veth pairs. This exact topology is what every hop number in every later section refers to.

NamespaceRoleTTL / Hop #Addressing
ns-clientApp client + path prober (C1)—10.10.1.1
ns-r1Forwarding routerTTL 1 → Hop 110.10.1.2 / 10.10.2.1
ns-r2Forwarding routerTTL 2 → Hop 210.10.2.2 / 10.10.3.1
ns-r3Forwarding router, primary fault-injection point in the demo scriptTTL 3 → Hop 310.10.3.2 / 10.10.4.1
ns-r4Forwarding routerTTL 4 → Hop 410.10.4.2 / 10.10.5.1
ns-serverApp server + probe responderTTL 5 → Hop 5 (Server)10.10.5.2

Each ns-r{N} has net.ipv4.ip_forward=1 and exactly two routes: a default route toward the server side (next hop's near address) and one specific route back toward 10.10.1.0/24 summarized for the client side. Because the topology is strictly linear, no dynamic routing protocol is needed — every route is a static one-liner, which also means route flapping (a §16 failure case in the review) cannot occur inside the testbed itself; it is reproduced only synthetically, if at all, as a stretch-goal experiment, never by accident.

Each ns-r{N} ↔ ns-r{N+1} veth pair is a dedicated /30 subnet, matching the table above. tc qdisc … netem is attached to the egress side of each router's server-facing interface — i.e., an impairment "at Hop 3" is applied to ns-r3's interface facing ns-r4, so it affects everything from that point forward, matching the persistence pattern the localization algorithm (review §11) is built to detect.

Terminology (C8)

Injecting netem at ns-r3's egress interface impairs that link segment — it says nothing about whether a real router at that position would itself be faulty. Every reference to this, in code and in the UI, is written as "degradation first appears at/after Hop 3" or "Hop 3 onward," never "Hop 3 caused the lag" or "the Hop 3 router is faulty."

§04

Fault-Controller Isolation

Locked Isolation is enforced at three independent layers, so that no single mistake (a wrong file permission, a stray import) leaks ground truth into the engine:

Process / OS-user layer

The fault controller runs as OS user hoptrace-truth. The correlation engine and Analysis API run as OS user hoptrace-engine. Neither is a member of the other's group.

Filesystem layer

The ground-truth log (GroundTruthEvent records, §06) is written to a SQLite file owned by hoptrace-truth:hoptrace-truth, mode 640. hoptrace-engine has no read bit. The evaluation harness (§09) runs as a third user, hoptrace-eval, which is the only account in the hoptrace-truth group and can therefore read the log — and only the log; it has no write access to it either, so the evaluation harness cannot retroactively "correct" ground truth to fit results.

Network layer

The fault controller's only network capability is executing ip netns exec ns-r{N} tc qdisc … against the host's own namespaces — it opens no listening socket and is not reachable from ns-client or ns-server. The Analysis API (§07) exposes no endpoint that accepts a hop number and returns or echoes ground-truth data.

Why three layers, not one

A single-layer control (e.g. "the engine's code just doesn't read that file") is a convention, not an isolation guarantee — it's exactly the kind of shortcut that quietly makes the Phase 5 evaluation circular if a future contributor adds a debugging endpoint that happens to expose it. Three independent layers mean a mistake in one doesn't compromise the guarantee.

Sequencing note

This architecture is fully realized starting Phase 3, when the fault controller and ground-truth log first exist. Phase 0 builds none of it — no hoptrace-truth/hoptrace-engine/hoptrace-eval users, no SQLite file, no permission bits. Phase 0's job is the raw namespace topology and a manually-driven tc netem impairment; see the companion Phase 0 Implementation Plan for the exact sequencing and what stays untouched.

§05

Measurement Protocol

Path prober

  • Open → Phase 1 experiment Probe transport is not locked to UDP. UDP and TCP SYN TTL probing are both Phase 1 candidates, compared on the testbed (methodology below) and selected for whichever gives the more useful, reliable correlation signal against the TCP/WebSocket application traffic. run_probe_round() (§07) takes a transport parameter so the choice is a configuration value, not a rewrite.
  • Locked Flow consistency regardless of transport: one 5-tuple per probing round (UDP: fixed destination port per round, starting at 33434, incrementing only between rounds; TCP SYN: fixed source port per round), so every probe within a round hashes identically under ECMP (paris-traceroute style).
  • Locked TTL sweep: 1 through 5 every round (matches §03's five measurable hops).
  • Locked Samples per hop per round: 2.
  • Locked Round interval: 500 ms — yields 4 RTT samples per hop per second.
  • Locked Per-probe timeout: 300 ms. A probe with no ICMP Time-Exceeded/port-unreachable (UDP) or no SYN-ACK/RST-with-TTL-exceeded (TCP) reply within the timeout is recorded as responded: false, never silently dropped from the record.
  • Locked A hop is marked UNKNOWN for a round if both its samples in that round are non-responses.

Transport selection experiment (Phase 1)

Run both transports, unchanged otherwise, across a short calibration set on the Phase 0 testbed (baseline + a handful of impairment trials reusing the Phase 0 acceptance scenario). Compare on: (1) response rate per hop — does one transport get silently deprioritized more than the other by the namespace routers' own handling; (2) RTT variance at baseline — a noisier transport degrades every downstream changepoint detector regardless of which one is chosen in §08; (3) closeness to the application's own transport family (TCP SYN is a strictly better proxy for a TCP/WebSocket app's treatment than UDP, but costs more to implement correctly — full handshake-avoidance and RST handling). Document the tradeoff and the chosen default in a short note before Phase 1 is marked complete; keep the losing transport's code path behind the same interface rather than deleting it, since the tradeoff may need revisiting once real fault data exists.

Application telemetry

  • Locked Transport: WebSocket over TCP, one persistent connection for the trial's duration.
  • Locked ping message cadence: 20 Hz (every 50 ms), each carrying a monotonic seq and the client's t_send_mono_ns; server echoes seq immediately on receipt. RTT is computed entirely client-side as t_recv_mono_ns − t_send_mono_ns (design rationale: review §9).
  • Locked interaction message: sent at a Poisson-distributed mean rate of 2/sec (models bursty user input rather than a metronome); server must reply with interaction_ack within a 150 ms target budget. A late or missing ack is a distinct app-level symptom from raw ping RTT and is logged as its own series.

Responded clarification (locked before Phase 3)

A missing response is not a slow response. Three states, never collapsed: (1) responded within budget — responded=true, rtt_ms real, missed_budget=false; (2) responded late — responded=true, rtt_ms real >150, missed_budget=true; (3) missing — responded=false, rtt_ms=null, and missed_budget=null for interaction (or false for ping, which has no budget concept at all). Earlier Phase 2 code set missed_budget=true for a missing interaction reply — representing "never arrived" as if it were a measured over-150ms RTT. Corrected: null means "budget not evaluable," not "budget met" or "budget missed by a number."

§08

Algorithm Candidates & the Changepoint Selection Experiment

This is the addition requested beyond the original review. detect_onset() (§07) is implemented once, but which algorithm sits behind it is not assumed — it's selected by running all candidates against real testbed traces before Phase 4 is finalized.

Candidates

CandidateTypeNote
A. Fixed-threshold baselinestrawmanFlags rolling mean + k·σ exceeded. Included only as the control every other candidate must beat — never a deployment candidate.
B. Two-sided CUSUMsequential, O(1)/sampleClassic, cheap, easy to explain in a viva; no native uncertainty output.
C. Bayesian Online Changepoint Detection (BOCPD)online, probabilisticAdams & MacKay (2007). Produces a run-length posterior — a natural fit for the confidence tag in §06's EvidenceRecord.
D. PELToffline/batch, exactKillick et al. (2012), via the ruptures library. Higher offline accuracy; not natively streaming — would need periodic re-runs over a sliding window, a real cost against the 500 ms probe cadence.
E. Rolling robust z-score (MAD-based)nonparametricRobust to the heavy-tailed noise typical of network RTT; simplest to reason about.

Experiment protocol

  1. Tuning-set collection (Phase 4a). Run a reduced fault matrix — 4 hops × 2 impairment types (latency, loss) × 3 magnitudes × 5 repeats = 120 trials — purely to generate labeled raw traces. This set is used only to choose the algorithm and is never reused in the Phase 5 reported evaluation numbers, to avoid tuning the algorithm on the same data used to score it.
  2. Uniform pipeline. Each candidate is substituted into detect_onset() and run through the unchanged stage-2/stage-3 pipeline, so what's compared is end-to-end localization behavior, not raw changepoint accuracy in isolation.
  3. Hard gate. Any candidate whose false-positive rate on no-fault control trials exceeds 5% is eliminated before ranking, regardless of its accuracy elsewhere — a detector that cries wolf is disqualified outright, not merely penalized.
  4. Ranking, survivors only. Weighted comparison on: (1) within-±1-hop localization accuracy [primary], (2) detection latency, (3) computational feasibility at the 500 ms probe cadence [disqualifying for D unless a windowed variant is shown to keep pace], (4) whether the method natively exposes an uncertainty signal usable by the confidence model.
  5. Freeze, once, before Phase 5 (C9). The winning algorithm's hyperparameters, the δ_align tolerance (§07), and the confidence-score weights (§06 EvidenceRecord) are fitted using only Phase 4a data and then frozen as one artifact. Phase 5's held-out test set is never touched during this step, and once frozen, none of these four values may be revisited using Phase 5 results — a poor Phase 5 outcome is reported as-is, not fed back to retune Phase 4.
  6. Output. A one-page selection report — scores per candidate, eliminations and why, the chosen method, and a documented runner-up fallback — becomes a required Phase 4 gate deliverable (§10).
§09

Evaluation Methodology

Magnitude definition

Locked Magnitude is defined relative to each trial's own pre-fault baseline noise, using median absolute deviation (MAD) rather than standard deviation, because RTT distributions are right-skewed and MAD is more robust to that skew: mild = onset shift of 2–4× baseline MAD, moderate = 4–8×, severe = >8×. For loss and bandwidth impairments, magnitude is expressed directly (loss %, capped Mbps) and independently binned into the same three labels via a fixed lookup table established during Phase 0a calibration runs.

Full evaluation matrix (Phase 5, disjoint from the Phase 4a tuning set)

FactorLevels
Fault locationhop 1, 2, 3, 4
Fault typelatency, jitter, loss, bandwidth cap
Magnitudemild, moderate, severe
Durationtransient (5 s), sustained (60 s)
Probe conditionsnormal, one non-responding hop, simulated ICMP/UDP rate-limit

4 × 4 × 3 × 2 × 3 = 288 cells. Open repeats per cell — no count is locked here. §10's Phase 5a pilot procedure determines it before the full matrix runs.

Repeat-count procedure (Phase 5a pilot — replaces the earlier fixed default)

  1. Run a small pilot: 3 repeats × a representative subset of cells (one per fault type, at moderate magnitude, at hop 2 and hop 3) — roughly 24 pilot trials, drawn from the same held-out test conditions as the real matrix but not reused inside it.
  2. From the pilot, measure: per-trial wall-clock runtime (drives how long the full matrix will take), and the observed variance and effect size of the localization-accuracy and detection-latency metrics within each pilot cell.
  3. Run a simple power/sample-size calculation (e.g. a two-proportion or standard effect-size power calculation appropriate to the accuracy metric in §09) using the pilot's observed variance, targeting a stated power (e.g. 0.8) to detect the smallest effect size the project cares about distinguishing.
  4. Propose the minimum defensible repeat count and the resulting total runtime for the full 288-cell matrix, for approval, before Phase 5 executes at scale. 15/cell was an unvalidated placeholder in the prior revision of this document and is withdrawn — the pilot's numbers govern instead.

Metric formulas

  • Within-±1-hop accuracy = trials where |reported_hop − ground_truth_hop| ≤ 1 ÷ total detected trials.
  • False attribution rate = trials where confidence ∈ {high, medium} AND reported hop range excludes the true hop, ÷ total trials — the single number the review's honesty requirement lives or dies on.
  • Detection latency = t_onset_reported − t_start_mono_ns (from the matching GroundTruthEvent, joined only by the evaluation harness).
  • Calibration = a reliability diagram binning trials by reported confidence.score decile against observed within-±1-hop accuracy in that bin, plus a Brier score as a single summary number.
§10

Phase Gates & Success Criteria

Each gate is a go/no-go checklist. A phase is not "done enough" to start the next — every item must pass.

Phase 0

Testbed skeleton

  • All six namespaces reachable end-to-end; ping ns-client → ns-server shows 0% loss over 200 packets.
  • Standard traceroute/mtr run from ns-client shows exactly the 5 hops in §03, in order, on two consecutive runs.
  • A manual tc netem delay 100ms at ns-r3 changes observed RTT to ns-server by 100 ms ± 10%, confirmed via tc -s qdisc show and a follow-up ping; removing it restores baseline.
Phase 1

Path measurement engine

  • Hop identity matches §03's topology in ≥99% of 200 consecutive rounds (linear static-route topology, so near-100% is expected — anything lower indicates a probing bug, not real-world ECMP noise).
  • A deliberately firewalled router (drop rule on one ns-r{N}) is correctly reported as UNKNOWN for that hop, not silently omitted or interpolated.
Phase 2

Application telemetry

  • 5-minute unimpaired run: ping RTT std-dev < 5 ms, zero sequence gaps.
  • interaction_ack budget-miss rate is 0% at baseline, confirming the 150 ms budget is not itself the noise source.
Phase 3

Fault-injection controller

  • All four impairment types injectable/removable at all four router hops, logged start/end within ±50 ms of the actual tc command's execution.
  • Isolation check: a process running as hoptrace-engine attempting to read the ground-truth SQLite file receives a permission error, verified by an explicit negative test, not just absence of a code path.
Phase 4

Correlation engine + algorithm selection

  • Phase 4a tuning-set collection (120 trials) complete; §08 selection report produced and reviewed.
  • Chosen algorithm, on the tuning set, achieves within-±1-hop accuracy ≥ 80% and false-attribution rate ≤ 10% — thresholds are provisional pending the Phase 4a data itself (§11.7) but the engine may not proceed to Phase 5 below them.
  • Algorithm, hyperparameters, δ_align, and confidence weights are frozen as one artifact per C9 — dated, recorded, and not touched again regardless of Phase 5 outcome.
Phase 5a

Repeat-count pilot

  • ~24-trial pilot run (procedure in §09) complete; runtime, variance, and effect size measured.
  • Power/sample-size calculation performed and a minimum defensible repeat count proposed, with the resulting full-matrix runtime — submitted for approval before Phase 5 proper begins.
Phase 5

Evaluation harness

  • Full matrix (§09) executed on the held-out set with the Phase 5a-approved repeat count — never the withdrawn 15/cell placeholder.
  • All metrics in §09 computed and reported, including the ones that aren't flattering.
  • Calibration check passes: mean accuracy in the top confidence decile is statistically greater than in the bottom decile (simple proportion test is sufficient) — if it doesn't, the confidence model is broken and Phase 6 (UI/demo) does not start until it's fixed.
  • Per C9: no value frozen in Phase 4 is adjusted as a result of this phase, even if results disappoint.
§11

Remaining Technical Ambiguities

These are not oversights — each is either genuinely undecided or deliberately deferred to data the project doesn't have yet. Coding on Phase 0–3 can start without resolving any of them; Phase 4 cannot conclude without resolving 11.4–11.7.

Open

11.1 — Confidence score weighting. §06's confidence.factors lists named inputs, but the exact weighted formula turning them into a 0–1 score is not fixed here. Per C9, it is fitted only from Phase 4a tuning data, frozen alongside the chosen algorithm at the end of Phase 4, and never revisited using Phase 5 results — the earlier draft of this item incorrectly proposed deriving it from a "Phase 5 tuning pass," which is now explicitly prohibited.

Open

11.2 — Implementation language. Python or Go for the prober/engine is functionally interchangeable against every interface in §07. Not specified here; pick based on whichever the implementer is faster in, since the spec doesn't depend on the choice.

Open

11.3 — Trials per matrix cell. No longer a proposed default. §09/§10 now specify a Phase 5a pilot (~24 trials) followed by a power/sample-size calculation; the resulting repeat count is proposed for your approval before the full 288-cell matrix runs. The withdrawn 15/cell placeholder should not be used for planning purposes — it was unvalidated.

Open

11.4 — BOCPD hazard-rate / PELT penalty hyperparameters. Both require a tuning constant, fitted from Phase 4a data only and frozen at the same time as the confidence weights (C9). Whether the constant is tuned once globally or per-series is itself part of what the §08 selection experiment needs to decide — flagged here because it's easy to accidentally hard-code a value while building the candidates rather than treating it as part of the experiment.

Open → Phase 1 experiment

11.5 — Probe transport. Resolved into a concrete Phase 1 experiment rather than left as an unresolved tradeoff — see §05, "Transport selection experiment." UDP and TCP SYN are both implemented behind the same run_probe_round(transport=...) interface (§07) and compared on the testbed before one is chosen as the default; the losing transport's code path is kept, not deleted, since the choice may need revisiting once real fault data exists.

Open

11.6 — δ_align tolerance. Stage 2 (§07, align_and_localize) needs a tolerance window for "concurrent" onsets. A reasoned starting default is ~3× the probe round interval (1.5 s). Per C9, the final value is fitted from Phase 4a traces only, frozen with the algorithm and confidence weights at the end of Phase 4, and not adjusted using Phase 5 data.

Open

11.7 — Phase 4 accuracy thresholds (80% / 10%). Stated as provisional gate numbers in §10. They're reasonable targets, not derived from any prior data about this specific testbed — if the Phase 4a tuning set shows every candidate topping out lower, the threshold needs revisiting rather than being treated as a hard requirement that blocks the whole project.

Open

11.8 — Live-demo target and server placement. Out of scope for Phase 0–5 (which is testbed-only per C2), but flagged now because it affects whether any Phase 6 demo infrastructure needs to be provisioned in parallel. Needs an authorized destination named explicitly before that phase, not assumed.
