1

Environment Decision

WSL2, running Ubuntu 24.04 LTS. Not a standalone VM.

Why

  • WSL2 runs a real, lightweight Linux kernel (not a compatibility shim like WSL1) — ip netns, veth, and tc qdisc … netem behave identically to bare-metal Linux. Nothing in the spec's testbed design (§03) needs to change for WSL2 specifically.
  • It's free, officially supported on this machine (Windows 11, build 26200 — confirmed by inspection), and avoids provisioning, licensing, or paying for a separate VM.
  • A remote cloud VM was considered and rejected for Phase 0: it would reintroduce a second host into the loop, which is exactly the cross-host problem constraint C1 (single clock, co-located client + prober) was designed to eliminate. Keeping everything — Windows host, WSL2 Linux kernel, all six namespaces — on one physical machine keeps that constraint trivially true throughout Phase 0–5, not just in the app-telemetry component.
  • Lighter weight than a full VM (VirtualBox/VMware/Hyper-V standalone guest): faster to start/stop, shares the host filesystem, no separate resource allocation to manage for a project this size.

Current state (inspected)

  • wsl --status reports: not installed.
  • OS: Windows 11 Home Single Language, build 26200, 64-bit — WSL2-eligible.
Why I'm not installing this myself

Enabling WSL requires turning on the "Virtual Machine Platform" and "Windows Subsystem for Linux" optional Windows components, which needs administrator elevation and a reboot. That's a system-settings change, which I don't perform even with explicit approval — it's a standing rule, not a judgment call about this specific request. The commands below are for you to run, in an elevated PowerShell window, whenever you're ready:

run yourself, elevated PowerShell# installs WSL2 + Ubuntu-24.04, then prompts for reboot
wsl --install -d Ubuntu-24.04

# after reboot, first launch of Ubuntu-24.04 will prompt for a UNIX username/password
# then confirm the kernel and distro version:
wsl --status
wsl -l -v

Everything from §2 onward assumes that's done and you have an interactive shell inside Ubuntu-24.04 under WSL2. All remaining Phase 0 commands run inside that WSL2 shell, not in PowerShell.

lib/common.sh

#!/usr/bin/env bash
# sourced by every other Phase 0 script — single source of truth for names/addresses
set -euo pipefail

NODES=(ns-client ns-r1 ns-r2 ns-r3 ns-r4 ns-server)   # index 0..5
ROUTERS=(ns-r1 ns-r2 ns-r3 ns-r4)                     # the four forwarding namespaces

# subnet N (1..5) = 10.10.N.0/30 ; low-index node = .1, high-index node = .2
subnet() { echo "10.10.$1.0/30"; }
addr_lo() { echo "10.10.$1.1"; }   # address of NODES[$1-1] in subnet $1
addr_hi() { echo "10.10.$1.2"; }   # address of NODES[$1]   in subnet $1
veth_a() { echo "veth-s$1-a"; }    # host-side name of subnet $1's pair, low-index end
veth_b() { echo "veth-s$1-b"; }    # high-index end

setup_topology.sh

#!/usr/bin/env bash
set -euo pipefail
DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$DIR/lib/common.sh"

# 1. create namespaces
for ns in "${NODES[@]}"; do
  ip netns add "$ns"
done

# 2. create the 5 veth pairs and move each end into its namespace
for i in 1 2 3 4 5; do
  a="$(veth_a $i)"; b="$(veth_b $i)"
  ip link add "$a" type veth peer name "$b"
  ip link set "$a" netns "${NODES[$((i-1))]}"
  ip link set "$b" netns "${NODES[$i]}"
  ip netns exec "${NODES[$((i-1))]}" ip addr add "$(addr_lo $i)/30" dev "$a"
  ip netns exec "${NODES[$i]}"       ip addr add "$(addr_hi $i)/30" dev "$b"
  ip netns exec "${NODES[$((i-1))]}" ip link set "$a" up
  ip netns exec "${NODES[$i]}"       ip link set "$b" up
  ip netns exec "${NODES[$((i-1))]}" ip link set lo up
  ip netns exec "${NODES[$i]}"       ip link set lo up
done

# 3. enable forwarding on the four router namespaces only
for r in "${ROUTERS[@]}"; do
  ip netns exec "$r" sysctl -qw net.ipv4.ip_forward=1
done

# 4. static routes — explicit per-subnet, no aggregation (see plan §3 rationale)
ip netns exec ns-client ip route add 10.10.0.0/16 via 10.10.1.2

ip netns exec ns-r1 ip route add 10.10.3.0/30 via 10.10.2.2
ip netns exec ns-r1 ip route add 10.10.4.0/30 via 10.10.2.2
ip netns exec ns-r1 ip route add 10.10.5.0/30 via 10.10.2.2

ip netns exec ns-r2 ip route add 10.10.1.0/30 via 10.10.2.1
ip netns exec ns-r2 ip route add 10.10.4.0/30 via 10.10.3.2
ip netns exec ns-r2 ip route add 10.10.5.0/30 via 10.10.3.2

ip netns exec ns-r3 ip route add 10.10.1.0/30 via 10.10.3.1
ip netns exec ns-r3 ip route add 10.10.2.0/30 via 10.10.3.1
ip netns exec ns-r3 ip route add 10.10.5.0/30 via 10.10.4.2

ip netns exec ns-r4 ip route add 10.10.1.0/30 via 10.10.4.1
ip netns exec ns-r4 ip route add 10.10.2.0/30 via 10.10.4.1
ip netns exec ns-r4 ip route add 10.10.3.0/30 via 10.10.4.1

ip netns exec ns-server ip route add 10.10.0.0/16 via 10.10.5.1

echo "topology up."

Each router gets exactly one specific route per non-adjacent subnet (3 each), aimed at the correct-direction neighbor. This is deliberately unaggregated — easy to audit line-by-line against the address table, at the cost of 14 lines instead of a clever CIDR summary. For a 6-node linear topology, auditability wins.

teardown_topology.sh

#!/usr/bin/env bash
DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$DIR/lib/common.sh"
for ns in "${NODES[@]}"; do
  ip netns delete "$ns" 2>/dev/null || true
done
echo "torn down (namespaces removed; their veth halves go with them)."

impair_hop.sh manual, Phase 0 only

#!/usr/bin/env bash
# usage: impair_hop.sh <hop 1-4> <delay_ms>
# applies on the router's SERVER-FACING interface, matching spec §03/§08:
# "Hop N onward" impairment, never framed as "Router N is faulty" (C8).
set -euo pipefail
hop="$1"; delay_ms="$2"
router="ns-r${hop}"
iface="$(veth_b $((hop+1)))"   # router's far-side interface, from lib/common.sh
ip netns exec "$router" tc qdisc add dev "$iface" root netem delay "${delay_ms}ms"
echo "applied: ${delay_ms}ms delay on ${router}'s link segment toward hop $((hop+1))+ (NOT a claim that $router is faulty)"

clear_impairment.sh manual, Phase 0 only

#!/usr/bin/env bash
# usage: clear_impairment.sh <hop 1-4>
set -euo pipefail
hop="$1"; router="ns-r${hop}"; iface="$(veth_b $((hop+1)))"
ip netns exec "$router" tc qdisc del dev "$iface" root netem 2>/dev/null || true
echo "cleared impairment on ${router}."
These two scripts are scaffolding, not the fault controller

They exist only to satisfy Phase 0's "demonstrable 100 ms netem impairment that can be applied and removed" acceptance criterion. They are hand-run from a shell, log nothing, and have none of the isolation properties specified in §04 of the amended spec. Phase 3 replaces them entirely with the real fault-injection controller — these are not a head start on that component, and should not be extended toward it (§7).

Verification Tests

Test 1 — Zero-loss baseline connectivity

ip netns exec ns-client ping -c 200 -i 0.02 10.10.5.2

Pass: 0% packet loss in the summary. This is the direct check behind the "zero-loss baseline connectivity" acceptance item.

Test 2 — Exactly 5 hops, in order, twice

ip netns exec ns-client traceroute -n 10.10.5.2
ip netns exec ns-client traceroute -n 10.10.5.2   # run again — must match
# or, for a live view:
ip netns exec ns-client mtr -n -r -c 20 10.10.5.2

Pass: both runs show exactly 10.10.1.2 → 10.10.2.2 → 10.10.3.2 → 10.10.4.2 → 10.10.5.2, in that order, with no * (non-responding) entries. Requires installing traceroute and mtr-tiny (§3's only two non-default packages).

Test 3 — netem impairment applies, measures, and clears

# baseline
ip netns exec ns-client ping -c 20 10.10.5.2 | tail -1
# apply 100ms at hop 3 (ns-r3's link toward ns-r4/server)
./impair_hop.sh 3 100
ip netns exec ns-r3 tc -s qdisc show dev veth-s4-b
ip netns exec ns-client ping -c 20 10.10.5.2 | tail -1
# remove and confirm recovery
./clear_impairment.sh 3
ip netns exec ns-client ping -c 20 10.10.5.2 | tail -1

Pass: impaired-run mean RTT is baseline + 100 ms ± 10%; tc -s qdisc show confirms the netem qdisc is attached during the impaired window; post-clear ping returns to within baseline ± normal jitter.

verify_topology.sh

Wraps Tests 1–3 into one script that prints PASS/FAIL per check rather than requiring each command to be read by eye — genuinely useful once this is run more than once, which it will be.

#!/usr/bin/env bash
set -euo pipefail
DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$DIR/lib/common.sh"

pass() { echo "PASS: $1"; }
fail() { echo "FAIL: $1"; exit 1; }

loss=$(ip netns exec ns-client ping -c 200 -i 0.02 10.10.5.2 | grep -oP '\d+(?=% packet loss)')
[[ "$loss" == "0" ]] && pass "zero-loss baseline (200/200)" || fail "baseline loss = ${loss}%"

hops=$(ip netns exec ns-client traceroute -n -q1 10.10.5.2 | tail -n +2 | awk '{print $2}' | tr '\n' ' ')
expected="10.10.1.2 10.10.2.2 10.10.3.2 10.10.4.2 10.10.5.2 "
[[ "$hops" == "$expected" ]] && pass "5 hops in order: $hops" || fail "hop sequence mismatch: got [$hops]"

echo "run Test 3 (netem apply/measure/clear) manually — see plan §4, it needs a before/after comparison a script shouldn't silently average away."

ip netns exec: Operation not permittedNot running as root inside WSL2All Phase 0 scripts need root inside the WSL2 shell — run with sudo or as a root shell; this is normal for namespace/tc manipulation and not specific to this project.
Traceroute shows the right hops but occasionally a *Default per-hop probe count/timeout in traceroute is aggressive for a freshly-up namespace linkRe-run; if persistent, increase per-hop queries (traceroute -q 3) — this is a traceroute-tool tuning issue in Phase 0, unrelated to the custom prober's own retry logic that Phase 1 builds separately.

General reset procedure if anything is ambiguous: teardown_topology.sh, confirm ip netns list prints nothing, confirm no stray veth-s* interfaces remain in the root namespace with ip link show, then re-run setup_topology.sh from a clean state. Idempotent teardown-then-setup is the supported recovery path for every failure mode above except the WSL2 VM hang, which needs the `wsl --shutdown` step first.

Phase 0 Acceptance Criteria

Restated as a checklist — matches the Phase 0 gate in the amended spec §10 exactly, no additions.

  • WSL2 with Ubuntu 24.04 running; ip netns and tc available and functional.
  • All six namespaces (ns-client, ns-r1…ns-r4, ns-server) created with the exact addressing in §3.
  • Static routing verified: ns-client → ns-server reachable, and vice versa.
  • Test 1 passes: 200/200 packets, 0% loss, unimpaired.
  • Test 2 passes: traceroute/mtr shows exactly the 5 expected hops, in order, on two consecutive runs.
  • Test 3 passes: a 100 ms netem impairment applied at Hop 3 changes measured RTT by 100 ms ± 10%, is confirmed via tc -s qdisc show, and is fully removable, with ping returning to baseline afterward.
  • verify_topology.sh exists and its automatable checks (Tests 1–2) pass on a clean run.

No isolation-layer (OS users, permissions, ground-truth logging) criterion is included here — per amendment 5, that work starts in Phase 3, not Phase 0.
