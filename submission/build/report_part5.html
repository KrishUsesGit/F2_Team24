13. Limitations and Threats to Validity

Each limitation below is supported by a file in the repository; the source is given in brackets.

#LimitationDetail and consequence
1No independent validation of the current detectormad_sustained was never scored on data that its design had not seen. The one independent run (Phase 4, mad) missed its target at 3/12 = 25%. A sealed evaluation (spec Phase 5) has not been run. [docs/EVIDENCE_LEDGER.md]
2Exposed held-out setp4-held-* is permanently exposed; Phase 4b results on it are a historical record. The set was never sealed or made read-only. [ledger]
3Loss and bandwidth are not localized0/4 on the exposed held-out set (Phase 4 and 4b detectors) and 0/4 on the Phase 4b tuning set (all four candidates). Whether bandwidth limits are observable at all with the current light probe traffic is unproven; bandwidth is not de-scoped, and no investigation is authorized yet. [frozen_config_4b.json]
4Confidence is an uncalibrated heuristicA fixed formula based almost entirely on how many hops were unknown; the corroborating fraction is 1.0 whenever a range is reported. It is not a probability and does not reflect signal strength. Phase 4's high claims were 50% accurate. [correlate/evidence.py]
5Unknown hops cannot be assumed healthyA hop with too few responses is unknown, and "no corroborated onset" is not proof of health. A silent hop can also prevent localization, as in p4-held-12.
6Timing correlation is not causationHOPTRACE says when changes appear along an observed path. It does not establish which device, link or configuration caused them.
7"No onset" is ambiguousIt can mean healthy, a fault covering most of the window (global median/MAD baseline), or too little data. There is no "insufficient data" state. [demo script; ledger]
8Fixed, unvalidated parametersThe 1.5 s alignment window, the 500 ms bucket width (which also limits onset resolution), k_mad = 5, min_run = 3 and the 50% unknown threshold are fixed choices. [align.py, pipeline.py]
9Very small samples12 + 12 + 10 trials against a specified 120-trial tuning set and 288-cell matrix. Confidence intervals are wide (Section 12). [evaluate/power_calc.py]
10Controlled single-path testbedOne linear path, no ECMP, one application protocol, and ICMP error rate limiting deliberately switched off in the router and server namespaces. Behaviour on real routers and networks has not been evaluated. [setup_topology.sh]
11Ground-truth isolation is a permission testRoot can read the database; historical trial directory names encode the injected fault; evaluation result files contain labels and are world-readable on a Windows-mounted checkout. [README]
12Phase order and labelsThe UI and demo (Phase 6) were built before the Phase 5 evaluation, which the specification would not have allowed; several code comments use pre-numbering labels. [ledger]
13Demo scenario is favourableThe demo fault covers a minority of the window by construction; the first version (a majority) produced a false negative. [demo/demo_script.md]
14Dashboard limitsIt shows four stored trials, not live measurements; it has not been tested offline or across browsers; hop roles are a frontend constant, not a data field; there is no real "not localized" bundle and none was invented; the page is one ~500 kB script. [frontend/README.md]
15Documentation driftThe evidence ledger counts six exploratory p3-* trials, but five directories exist in experiments/; the figure used in this report is the directory count.

14.7 Selecting and running experiments

  • The recorded trials in experiments/ can be analysed again without a testbed. The four trials shown by the dashboard are those with a path_bundle.json.
  • Run your own trial on a built testbed (each command in the namespace shown; paths from the repository root, as root unless noted):
mkdir -p experiments/my-trial
ip netns exec ns-server python3 app/server.py --host 0.0.0.0 --port 8765 &
ip netns exec ns-client python3 prober/prober.py --dst 10.10.5.2 --src 10.10.1.1 --transport tcp_syn \
    --rounds 70 --interval 0.5 --out experiments/my-trial/hop.jsonl &
ip netns exec ns-client python3 app/client.py --host 10.10.5.2 --port 8765 --duration 35 \
    --out experiments/my-trial/app.jsonl &
# after ~25 s, inject a fault as the controller identity (hop 1-4; latency/jitter/loss/bandwidth):
su -s /bin/bash hoptrace-truth -c "cd faultctl && python3 controller.py inject --hop 2 --type latency --delay-ms 90 --trial-id my-trial"
# when the trial ends, clear it:
su -s /bin/bash hoptrace-truth -c "cd faultctl && python3 controller.py clear-latest --hop 2 --trial-id my-trial"

To analyse with the frozen configuration, mirror steps 5-6 of demo/run_demo.sh (demo/_run_engine_pipeline.py, then present/path_bundle.py). These manual commands are derived from the scripts' own argument parsers and docstrings; they were not executed for this report. Do not run the evaluate/ scripts on new data without reading Section 11 first.

15. Conclusion and Future Work

15.1 Conclusion

HOPTRACE demonstrates, on a controlled testbed, how an application's RTT and a path's per-hop RTT can be measured on a shared clock and compared to estimate where along an observed path application degradation appears to begin. The engineering is complete enough to run end to end: a six-namespace testbed, a raw-socket prober, a hand-written WebSocket application, a permission-isolated fault controller, a median/MAD correlation engine with typed evidence, an evidence-bounded interpretation layer and a dashboard that shows stored results. The checks run for this report all pass: 117 Python tests, 310 frontend tests, strict typecheck, zero-warning lint, a verified production build and distribution, 40 real-browser layout checks, a four-trial browser session and a live topology check.

The science is less settled than the engineering, and the project states so. The only independent evaluation missed its false-attribution target (3/12 = 25% against at most 10%). The revised detector met the numeric target only on a set it had been designed against (1/12 = 8.3%), which is not validation. Loss and bandwidth faults are not localized. Confidence is a fixed heuristic. These are results, not omissions, and the interface repeats them wherever a result is shown.

15.2 Future work (recorded, not yet authorized)

  1. Propose a feasible evaluation scope against the locked specification, with expected runtime and statistical limits, and obtain approval before any large run.
  2. Implement spec Phase 5: a sealed evaluation set, an evaluation harness and a calibration check of the confidence heuristic.
  3. Investigate whether controlled background traffic and a throughput-sensitive measurement make bandwidth impairment observable (and whether RTT is the wrong observable for loss).
  4. Add an explicit "insufficient data" result state so that "no onset" is no longer ambiguous.
  5. Validate or replace the fixed 1.5 s alignment window and the global-baseline assumption.
  6. Test the dashboard with the network disabled, across browsers, and from a clean clone; add a versioned schema for the stored bundle.
