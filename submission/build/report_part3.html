8.2 Routing and calibration

  • Forwarding and routes. net.ipv4.ip_forward=1 only in the four router namespaces. Static, explicit per-subnet routes (no aggregation); the client and server each have a single 10.10.0.0/16 route towards the path.
  • ICMP rate-limit calibration. Linux's default icmp_ratelimit allows about one ICMP error per second per namespace, which silently suppressed most hop replies at a 500 ms probe cadence (about 60% matched in an early run). The setup script sets icmp_ratelimit=0 inside the four router namespaces and the server namespace only. It does not disable packet loss or alter netem/tbf behaviour, and it does not touch the host's own namespace.

9. Algorithms and Methodology

9.1 Synchronisation into 500 ms buckets

Because the prober and the application client are separate processes with separate counters, there are no shared sequence IDs. Alignment instead uses the shared clock: all t_send_mono_ns values are placed on one timeline starting at the earliest sample, and divided into 500 ms buckets (the coarser of the two cadences; pings run at 20 Hz, probe rounds at 2 Hz). For bucket b, the application value is the mean RTT of the pings that responded in it, and the value for hop k is the mean RTT of the probes to TTL k that responded. A bucket with samples but no response is unknown; a bucket with no value is skipped by the detector and never interpolated.

9.2 Onset detection (median / MAD, sustained)

For one series with valid values x1…xn (n ≥ 5, otherwise no onset can be claimed):

m = median(x),   MAD = median(|xi − m|),   T = m + k·MAD   with k = 5 (k_mad)

The onset is the time of the first bucket of the first run of at least min_run = 3 consecutive values above T. A single noisy bucket above T does not count. (If the series is perfectly flat the MAD is replaced by 10-9 to avoid division by zero.) These are exactly the operations in detect_onset_mad_sustained (Section 7.3). Figure 4 shows them on the recorded demo-run-01.

9.3 Timing alignment and downstream persistence

Let tapp be the application onset and tk the onset of hop k (if any). Two onsets are concurrent when |tk − tapp| ≤ Δ with Δ = 1.5 s (three probe rounds; a documented default that has not been validated). The engine scans hops from the shallowest and reports the first hop c such that

  1. hop c has an onset concurrent with the application's, and
  2. every hop from c through the deepest measured hop also has a concurrent onset.

The second condition is the persistence test: a hop that spikes alone, with nothing downstream, is evidence against localizing there. The result is the range {min: c, max: deepest corroborating hop}. If there is no application onset, nothing is localized. If there is an application onset but no hop satisfies both conditions, the result is "not localized".

9.4 Evidence representation, confidence and interpretation

A hop is marked unknown if, among the buckets in which it was probed, at least 50% received no response at all (UNKNOWN_FRACTION_THRESHOLD = 0.5, fixed, not tuned). The confidence claim is the following fixed heuristic:

score = corroborating fraction × (1 − |unknown hops| / 5)    high ≥ 0.8 · medium ≥ 0.5 · low > 0 · otherwise insufficient

What the confidence score is, and is not
  • It is not a probability and has not been calibrated. It does not measure how strong the signal was.
  • Because the persistence rule already requires every downstream hop to corroborate, the corroborating fraction is 1.0 whenever a range is reported, so in practice the level depends only on how many hops were unknown: 0 unknown → 1.0 (high); 1 → 0.8 (high); 2 → 0.6 (medium); 3 → 0.4 (low).
  • The stored calibration tables show the weakness. In the independent Phase 4 run, the four high-confidence claims had an observed accuracy of only 0.5 (two of them were confident claims on clean controls); the Brier score was 0.432 (n = 5). In the exposed Phase 4b set the Brier score was 0.04 (n = 4), a figure from a small, inspected set and not evidence of calibration.

Interpretation then maps the record to one of the four locked sentences (Section 4.2): only high confidence yields "Degradation appears to begin at or after Hop N"; medium or low yields "Partially localized".

9.5 Limitations of the methodology

  • Global baseline. The threshold uses the median and MAD of the whole series. It assumes the fault covers a minority of the window so that the median still represents "normal". If a fault covers most of the window, the median sits inside the faulted region and the detector reports no onset. The demo script documents a first version with a 10 s baseline and 25 s fault that produced exactly this false negative; the recorded demo therefore uses a 25 s baseline and runs in the detector's favourable regime.
  • No "insufficient data" state. "No onset" cannot be distinguished from "the detector could not establish a baseline".
  • Near-silent series. On sub-millisecond hop series the MAD can be tiny, so the threshold becomes an almost-zero absolute gap; this was the diagnosed cause of clean-control false positives in Phase 4 and the motivation for requiring a sustained run.
  • Resolution. Onsets are quantised to 500 ms, and the 1.5 s alignment window is fixed and unvalidated.
  • RTT as the only observable. No candidate localized any loss or bandwidth trial. The project records, as an open and unresolved problem in frozen_config_4b.json, that RTT-based onset detection may be the wrong observable for these two fault types; this has not been tested further.
  • Correlation, not causation. Concurrent onsets are timing evidence only.

9.6 Algorithm selection (Phases 4 and 4b)
