Abstract

When a networked application slows down, the application can observe that it is slow but not where on the network path the slowdown starts. Conventional tools split the problem in two: ping and traceroute measure the path without knowing what the application experienced, while application monitoring measures the application without knowing the path. HOPTRACE joins the two views. It probes every hop of a path and samples the application's own round-trip time (RTT) on one shared clock, detects when each series starts to behave abnormally, and reports the earliest hop whose onset lines up in time with the application's. Its output is deliberately bounded: "Degradation appears to begin at or after Hop N." It never says that a particular router caused anything.

The system is implemented end to end on a controlled testbed of six Linux network namespaces (a client, four routers and a server). It consists of a raw-socket path prober, a hand-written RFC 6455 WebSocket application client and server, a fault controller that injects tc netem/tbf impairments with ground truth isolated by operating-system permissions, a correlation engine (median/MAD onset detection, timing alignment, typed evidence), an interpretation layer, and a React + TypeScript dashboard that displays stored results. All Python code uses only the standard library.

Evaluation was honest about failure. In Phase 4, the only independent held-out run, the selected detector (mad) missed the false-attribution target: 3/12 = 25% against at most 10%. A revised detector (mad_sustained, Phase 4b) scored 1/12 = 8.3%, but on the same held-out set after its traces had been inspected, so that figure is a historical record and not independent validation. Loss and bandwidth faults were not localized (0 of 4 on the exposed held-out set and 0 of 4 on the Phase 4b tuning set). Confidence is a fixed heuristic, not a probability.

1. Introduction and Problem Statement

A user reports that an application feels slow. The operator can look at the application's response times, and can run traceroute to list the routers along the way. What neither tool answers is the question that matters during diagnosis: at which point along the path did the application's degradation begin to appear?

Answering this requires the application's behaviour and the path's behaviour to be compared in time. If the application's RTT jumps at 25.0 s and the probe RTT to Hop 3 jumps at 25.0 s while Hops 1 and 2 stay flat, the evidence points at the segment between Hop 2 and Hop 3. If the two series use unsynchronised clocks, or if the probes are sent from a different place from where the application runs, that comparison is unreliable.

Problem statement. Given an application whose round-trip time degrades while a path of known hops is observed, estimate the earliest hop at which the degradation appears to begin, state the evidence and its limits, and refuse to claim a cause.

2. Project Objectives and Scope

2.1 Objectives

  1. Build a reproducible testbed in which the path has a known number of hops and faults can be injected on a chosen link.
  2. Measure the path hop by hop and the application's own RTT against a single shared clock.
  3. Detect, for every series, when it starts behaving abnormally, and align those onsets in time.
  4. Report the result in evidence-bounded language, keeping measured facts, inferences, correlations, confidence and unknowns visibly separate.
  5. Keep the record of what was injected (ground truth) out of reach of the localization engine, and score the engine only afterwards.
  6. Present stored results in an interactive dashboard that does not recompute or embellish them.
  7. Evaluate candidate detectors on separate tuning and held-out trial sets, and disclose the outcome, including misses.

3. Existing Problem and Motivation

ping and traceroute report per-hop reachability and RTT. They describe the path, but say nothing about what a particular application sees. Application performance monitoring has the opposite blind spot: it sees the symptom but not the path. A network engineer therefore correlates the two by hand, which is slow and hard to reproduce.

Two practical difficulties motivate HOPTRACE's design:

  • Clock alignment. To say that two onsets coincide, both measurements must share a timeline. HOPTRACE runs the prober and the application client in the same network namespace and reads the same CLOCK_MONOTONIC clock, so their timestamps are directly comparable without any clock synchronization protocol.
  • Honest uncertainty. Timing coincidence is not causation, and a hop that does not answer probes is not necessarily healthy. A tool that quietly turns missing data into a confident verdict is worse than no tool. HOPTRACE therefore keeps "unknown" as a first-class state and restricts its sentences to a fixed, evidence-bounded template.

4. Proposed Solution and Design Rationale

HOPTRACE runs a four-step loop: measure → detect → align → report.

  1. Measure. A raw-socket prober sends TTL-limited probes to hops 1–5 every 500 ms; an application client pings its server at 20 Hz. Both write timestamped JSON-lines files using one monotonic clock.
  2. Detect. Both streams are aggregated into 500 ms buckets. For each series the detector computes a median/MAD baseline and finds the first point where the series stays above median + 5·MAD for three consecutive buckets.
  3. Align. Starting from the shallowest hop, find the first hop whose onset is within 1.5 s of the application's onset and whose deeper hops also show concurrent onsets (persistence downstream).
  4. Report. Convert the result into a typed evidence record and a fixed-template sentence: "Degradation appears to begin at or after Hop N."

4.2 What the result means, and what it does not

The single most important design point is the boundary of the claim. HOPTRACE's output has exactly four result states, each with a locked sentence:

Result stateWhenLocked sentence (as in present/interpret.py)
LocalizedApplication onset found, hop range found, confidence high"Degradation appears to begin at or after Hop N."
Partially localizedHop range found, confidence medium or low"We detected degradation, but the exact location is uncertain."
Not localizedApplication onset found, no corroborated hop"We detected application degradation, but couldn't establish a reliable network-path location."
No degradationNo application onset detected"No significant degradation was detected during this test."
Reading the result correctly
  • The result says when changes were observed along the path, not why. It does not name a faulty device.
  • Timing correlation does not establish causation. A hop whose onset lines up with the application's is timing evidence only.
  • "No significant degradation was detected" means no onset was detected. It can also occur for a real fault that covers most of the observation window, or when there is too little data (Section 9.5).
  • Unknown ≠ healthy and confidence ≠ probability (Section 9.4).
