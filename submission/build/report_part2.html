5. System Architecture

HOPTRACE has two halves that are kept apart on purpose. The observation and analysis path measures, detects, aligns and presents. The experiment control and evaluation half injects faults, records what was injected, and scores results afterwards. Information flows from the second half to the first only through the physical network (the impairment itself), never as labels.

5.1 Network testbed

Six Linux network namespaces form a linear path: ns-client, ns-r1…ns-r4, ns-server, joined by five veth pairs on five /30 subnets (10.10.N.0/30). IP forwarding is enabled only in the four router namespaces; static routes are explicit per subnet. The probe path therefore has exactly five measurable hops: four routers and the server as Hop 5. Details are in Section 8.

5.2 Network path probing

prober/prober.py runs inside ns-client as root (raw sockets). In each round it sends two probes per TTL for TTL 1…5, sequentially (one outstanding probe at a time, one fixed 5-tuple per round), with a 0.3 s timeout; rounds start every 0.5 s. Two transports share one interface:

  • TCP-SYN (default in the demo and trials): a hand-built IP+TCP header with IP_HDRINCL, destination port 80; a router answers with ICMP Time-Exceeded, the server with a TCP reply.
  • UDP: destination port 33434 + round_id; routers answer with ICMP Time-Exceeded, the server with ICMP Destination-Unreachable.

Every probe becomes one HopSample row. A probe with no answer is recorded as responded: false with null IP and RTT; it is never interpolated.

5.3 Application telemetry

app/client.py opens one persistent WebSocket/TCP connection (the protocol is hand-implemented in app/ws_protocol.py following RFC 6455) from ns-client to app/server.py in ns-server. It sends a 20 Hz ping stream and a Poisson-arrival interaction stream (mean 2 events/s, 150 ms budget). The server only echoes sequence numbers; RTT is computed entirely client-side from the same CLOCK_MONOTONIC calls the prober uses. Three states are kept distinct: within budget, late (measured RTT above 150 ms, interactions only) and missing (no reply within 2 s; RTT stays null and is never recorded as a large number). Only the ping stream feeds the detector.

5.4 Correlation engine

correlate/ turns the two raw files into a typed result in four small modules (Figure 2): synchronize.py (common 500 ms timeline), onset_candidates_v2.py (the frozen mad_sustained detector), align.py (cross-series alignment and downstream persistence) and evidence.py (typed claims). pipeline.py orchestrates them. The engine reads only the two files it is given; there is no code path that could read what was injected.

5.5 Evidence and interpretation layer

The correlation engine's output is an EvidenceRecord: a list of claims, each carrying exactly one of five tags. present/interpret.py maps the record to one of four locked result sentences, present/technical_view.py exposes the underlying numbers, and present/path_bundle.py assembles the UI bundle. These modules perform no detection, alignment or confidence computation; they re-express stored fields and assert that no causal phrase ("caused", "is faulty", "is broken", "responsible for") is ever produced.

5.6 Frontend dashboard

frontend/ is a React + TypeScript (strict) + Vite + Tailwind + Motion application. It has no backend. A small Vite plugin serves an explicit allowlist of stored files (the four path_bundle.json files and two aggregate evaluation projections) in development and emits the same files into dist/data/ for the production build. The page shows the application's RTT chart, a three-dimensional client-to-server path with selectable hops, a per-hop inspector, the boundary statement, the evidence grouped by kind, the stored confidence and its limits, the stored evaluations, the limitations, and an optional guided explanation. The browser formats and displays stored values; it never recomputes an onset, a status or a confidence. Section 10 walks through it with screenshots.

5.7 Fault injection and ground-truth isolation

faultctl/controller.py runs as the OS user hoptrace-truth. It may reach tc inside the four router namespaces only, through a narrow sudoers rule created by faultctl/setup_identities.sh. Each injection records an event (trial, hop, type, magnitude, start/end time on the monotonic clock, the exact tc command) in a SQLite database at /var/lib/hoptrace/groundtruth.db, which is deliberately outside the repository on the native Linux filesystem (mode 0640, directory 0750). The analysis identity hoptrace-engine is not in that group and receives Permission denied; the evaluation identity hoptrace-eval is in the group and may read it. demo/run_demo.sh checks this live before injecting anything.

A fault at "hop N" is applied to the egress interface of ns-rN, i.e. the link leaving Hop N: Hop 1 → ns-r1:veth-s2-a, Hop 2 → ns-r2:veth-s3-a, Hop 3 → ns-r3:veth-s4-a, Hop 4 → ns-r4:veth-s5-a. Hop 5 (the server) is not a target. Consequently the first hop whose measurement can show the fault is N+1, and the evaluation scores against min(N+1, 5).

What the isolation does and does not guarantee
  • Does: an unprivileged analysis process cannot read the database (checked live by the demo script); correlate/ never imports the ground-truth module.
  • Does not: root can read the database; trial directory names for historical trials encode the fault type and hop; the evaluation result files in evaluate/ contain labels and are readable by any local process. It is a permission test, not a complete security audit.

5.8 Evaluation workflow

  1. Record trials (hop.jsonl, app.jsonl, a minimal trial_meta.json) while the fault controller injects (or does not inject) an impairment.
  2. Run candidate detectors on a tuning set; select one by a fixed rule (primary: within-one-hop accuracy; tie-breaks: false attribution, then Brier score) and write a frozen configuration file.
  3. Score the frozen configuration once on a held-out set as hoptrace-eval, which is the only place engine output is joined to ground truth.
  4. Report the metrics, including a Wilson 95% interval, and any failure.

The metrics are defined in evaluate/metrics.py. A false attribution is a confident (medium or high) claim that is either wrong or made on a clean control. The target for the project is at most 10%.

Sustained onset detection (correlate/onset_candidates_v2.py, the frozen Phase 4b detector; unchanged):

def detect_onset_mad_sustained(series, t, k_mad: float = 5.0, min_run: int = 3):
    values, times = _valid(series, t)
    if len(values) < MIN_VALID_POINTS:            # 5
        return None
    med = st.median(values)
    mad = st.median([abs(v - med) for v in values]) or 1e-9
    threshold = med + k_mad * mad
    run_start = None; run_len = 0
    for i, v in enumerate(values):
        if v > threshold:
            if run_start is None: run_start = i
            run_len += 1
            if run_len >= min_run:                # onset = first point of the run
                return OnsetResult(t_onset_ns=times[run_start],
                                   confidence_raw=(v - med) / mad, method=METHOD_MAD_SUSTAINED)
        else:
            run_start = None; run_len = 0
    return None

7.4 How the dashboard uses stored results

  • Data source. vite/hoptraceData.ts scans experiments/*/path_bundle.json and serves data/index.json, data/bundles/<id>.json and two aggregate projections of the evaluation files. Nothing else is reachable: raw traces (*.jsonl), the ground-truth database and arbitrary paths return no data (probed by about forty URLs in vite/devServer.test.ts).
  • Validation. Each bundle is checked against a Zod schema at load time; a malformed bundle shows an error state rather than a guess.
  • No recomputation. The browser formats stored values. Statuses, onsets, confidence and hop range come from the bundle.
  • Local-path hygiene. The historical demo bundle records an absolute machine path; the file on disk is left unchanged (it is evidence), the served copy keeps only the base name, and npm run verify:dist fails on any local path in dist/.
  • Illustration vs measurement. Moving packets in the 3-D scene are illustrative only; the bundles contain no packet-level observations, and the page says so next to the animation.

7.5 How impairments are configured and evaluated

The impairment type, hop and magnitude are chosen per trial and passed to faultctl/controller.py inject; clear-latest removes the open event by trial and hop. The historical trial sets used magnitude classes (mild, moderate, severe) and some transient faults that cover only part of the window; these are encoded in the trial directory names, not in a machine-readable file. For scoring, evaluate/metrics.py reads the ground-truth hop and takes expected_hop = min(hop_target + 1, 5).
